# Запись в Zephyr: создание тест-кейсов

Дата: 2026-09-19
Статус: согласовано, готово к планированию реализации

## Задача

Добавить в существующий `zephyr-mcp` запись. Сейчас сервер строго read-only:
девять tools, все на чтение.

Первая версия — один tool `create_test_case`. Правка кейсов, папки, циклы и
картинки — следующими версиями (см. «Дальнейшие версии»).

## Почему не берём готовый MCP

Проверялись три сторонних сервера. `leorosignoli/jira-zephyr-mcp` и
`metquay/zephyr-scale-mcp` написаны под Zephyr Scale **Cloud**: хост
`api.zephyrscale.smartbear.com/v2` зашит литералом, на нашем инстансе этот
путь отдаёт 302. `ArtyMaximus/zephyr-scale-mcp-server` написан под Server/DC
и работоспособен, но это Node (у нас Python + uvx), апстрим заброшен
(4 коммита, последний 2026-03-20), а в npm лежит версия без мартовского
фикса. Из него взяты сведения об API — эндпоинты и payload, — код не
переносится.

Подробности расхождения Cloud/ATM — в [CLAUDE.md](../../../CLAUDE.md).

## Выключатель `ZEPHYR_ALLOW_WRITE`

Переменная окружения, **по умолчанию выключена** (`0`). Включается значением,
не входящим в `{0, false, no, off, ""}` (регистронезависимо).

Отличие от `EWS_ALLOW_WRITE` в `outlook-mcp`, где запись включена по
умолчанию, осознанное: там правится свой календарь, здесь — общий Zephyr
команды. Обновление сервера у уже установленных сотрудников не должно молча
выдавать агенту право создавать кейсы в общем проекте.

При выключенном флаге пишущие tools **не регистрируются вовсе** — их нет в
`tools/list`. Как и в `outlook-mcp`: модель не видит инструмента и не пытается
его звать.

Install-скрипты переменную не спрашивают, она документируется в
`install/README.md`.

## Контракт API (проверен curl на живом инстансе)

`POST /rest/atm/1.0/testcase` → `201 {"key": "PROJ-T123"}`

Отправленный payload:

```json
{
  "projectKey": "PROJ",
  "name": "...",
  "objective": "...",
  "testScript": {
    "type": "STEP_BY_STEP",
    "steps": [{"description": "шаг 1", "expectedResult": "результат 1"}]
  }
}
```

Что подтвердило последующее чтение созданного кейса:

- шаги сохраняются **плоско** в `testScript.steps`, с проставленным `index`;
  обёртка `stepByStepScript` нужна только для `/rest/tests/1.0` и здесь
  неприменима;
- `status` (`Draft`), `priority` (`Normal`) и `majorVersion` (`1`)
  проставляет сервер — не отправляем, чтобы не хардкодить значения инстанса.

Путь `/rest/tests/1.0/testcase` тоже принимает создание (`201`), но кладёт
кейс с пустым `PLAIN_TEXT`-скриптом: имя записывается, шаги теряются. Второй
базовый путь в клиенте поэтому **не заводим** — весь ATM-контракт покрывает
`/rest/atm/1.0`.

**Проверено:** поле `folder` принимает путь строкой (`/Папка/Подпапка`) —
curl вернул `201`. Числовой `folderId` не понадобился.

## Архитектура

Границы модулей сохраняются как есть: `config.py` читает конфигурацию,
`client.py` знает HTTP и контракт ATM, `tools.py` объявляет tools.

**`config.py`.** В `Config` добавляется `allow_write: bool = False`. Читается
в `load_config()` рядом с обязательными переменными, но необязательна:
отсутствует → выключено, ошибки старта нет.

**`client.py`.** Один новый метод рядом с существующими, на том же
`API_BASE_PATH`:

```python
def create_test_case(self, project_key, name, steps, objective=None,
                     precondition=None, folder=None, labels=None) -> dict
```

Собирает payload по контракту выше, проставляет `index` шагам по порядку,
опциональные поля добавляет только непустыми. Возвращает ответ сервера как
есть (`{"key": ...}`).

Элемент `steps` — словарь с ключами `description` (обязательный),
`expectedResult` и `testData` (опциональные). `index` задаёт клиент по
позиции в списке, от вызывающего он не принимается.

**`tools.py`.** Сигнатура `register_tools` получает третий параметр:

```python
def register_tools(mcp: FastMCP, client: ZephyrClient, config: Config) -> None
```

Пишущий tool регистрируется под `if config.allow_write:`. Конфиг передаётся
явно, а не прячется в клиенте: tool зависит от настройки, клиент остаётся
носителем только HTTP-логики.

## Текстовые поля — HTML

ATM хранит `objective`, `precondition`, `description` и `expectedResult` как
HTML и отображает их с разметкой.

Решение: **вход трактуется как HTML и передаётся без изменений.**
Экранирования и markdown-конвертации нет.

Альтернатива (экранировать вход, конвертируя markdown) отвергнута: она
исключает разметку от модели, а смешивать два режима нельзя — угадывание
«теги или литерал» даёт баги.

Инструкция для модели задаётся в docstring tool и в описаниях параметров:
передавать готовый HTML-фрагмент (`<ul><li>`, `<b>`, `<br/>`), литеральные
`<` и `>` экранировать как `&lt;`/`&gt;`.

Белый список тегов в первой версии **не делаем**. Кейсы пишут свои
сотрудники, `<script>` в Zephyr никого не атакует, а ошибочную разметку
поправит `update_test_case` из следующей версии — как и любую другую ошибку
в созданном кейсе.

## Обработка ошибок

Отдельных типов ошибок не вводим. Существующий `ZephyrError(f"zephyr API
error {status}: {snippet}")` сохраняется для записи без изменений: тело
ответа ATM при `400` называет непринятое поле, при `403` — отсутствие прав.
Ошибка не проглатывается, а доходит до агента со статусом и текстом сервера;
собственные формулировки поверх чужих кодов устареют с версией плагина.

## Тестирование

По образцу `tests/test_client.py`, на замоканном транспорте, без сети:

- payload собирается по контракту: `testScript.type == "STEP_BY_STEP"`, шаги
  плоско в `testScript.steps` с `index` 0, 1, 2…;
- пустые опциональные поля в payload не попадают; `status`/`priority` не
  отправляются никогда;
- HTML в текстовых полях уходит неизменённым;
- ошибка сервера поднимается как `ZephyrError` со статусом;
- при `allow_write=False` tool не зарегистрирован, при `True` —
  зарегистрирован.

## Дальнейшие версии

- **v2:** `update_test_case` — правка кейса и шагов. Приоритет выше, чем у
  папок: это штатный способ исправить ошибку `create_test_case`. Механика —
  `PUT /rest/atm/1.0/testcase/{key}`; проверить curl, заменяет ли PUT объект
  целиком (тогда нужен read-modify-write, как сделано у ArtyMaximus).
  Затем `create_folder`, `create_test_run`, `add_test_cases_to_run`.
- **v3:** `upload_image` — картинки в шагах, `POST
  /rest/tests/1.0/attachment/embeddedimage`. Только с локальных путей
  пользователя; сетевой доступ по произвольному URL не реализуем. Чтение
  файла по пути от модели — доступ к ФС, путь потребует ограничения.

## Вне области

- Удаление кейсов и папок. Необратимо, делается руками в UI.
- Загрузка картинок по HTTP-ссылке.
- Автосоздание недостающих папок при создании кейса: скрытая запись, которую
  пользователь не заказывал (опечатка в пути порождает дерево папок).
- Подбор папки эвристикой по описанию кейса — это работа модели, не сервера.
- Существующие читающие tools не трогаются: их оптимизации (батчи по 100
  ключей из-за `414`, sparse fieldset, client-side фильтр по префиксу папки)
  остаются как есть.
