# Запись в календарь: create/update/delete событий

Дата: 2026-08-15
Статус: согласовано, готово к планированию реализации

## Задача

Добавить в существующий `outlook-mcp` три MCP-tool для работы с календарём:
`create_event`, `update_event`, `delete_event`. Сейчас сервер строго
read-only.

## Отмена read-only

README (раздел «Не делать»), CLAUDE.md и текст `--help` в `server.py`
объявляют сервер read-only. Это ограничение снимается **только для
календаря**. Почта остаётся read-only без оговорок: ошибочно созданную
встречу видно в своём календаре и её можно удалить, ошибочно отправленное
письмо необратимо.

Новая формулировка правила: «никакой записи в почту; календарь — только
через явные пишущие tools».

### Выключатель `EWS_ALLOW_WRITE`

Переменная окружения, **по умолчанию включена**. Выключается значениями
`0`/`false`/`no` (регистронезависимо). Install-скрипты её не спрашивают —
она документируется в `install/README.md` как способ получить read-only
сервер.

При выключенном флаге пишущие tools **не регистрируются вовсе** — их нет в
`tools/list`. Это осознанно сильнее, чем «зарегистрированы и отказывают»:
LLM не видит инструмента и не пытается его звать, вместо того чтобы
упереться в отказ и искать обход.

Флаг читается из `_config`, создаваемого через `load_config()` на импорте
модуля, то есть до ленивой валидации. Это допустимо: переменная
необязательна и не валидируется (отсутствует → включено). Инвариант
«сервер стартует и отдаёт `tools/list` без реальных кредов» сохраняется.

## Архитектура

Новый модуль `src/outlook_mcp/calendar_write.py`. Логика записи **не**
дописывается в `calendar_service.py`: тот уже 574 строки, и большая часть —
алгоритм `find_free_slots` (слоты, busy-типы, диагностика). Читающая часть
остаётся нетронутой.

Переиспользуется:

- `decode_item_id` / `encode_item_id` / `format_event_details` из
  `formatting.py` — форма ответа совпадает с `get_event`;
- `translate_ews_error` из `ews_client.py`;
- `_validate_emails` из `server.py` — уже нормализует, дедуплицирует и
  ограничивает список 20 адресами;
- `_fetch_one` и `_find_by_id_in_calendar` из `calendar_service.py` —
  получение item по `(id, changekey)` с fallback-разрешением устаревшего
  ChangeKey. `calendar_service.py` остаётся владельцем этого кода,
  `calendar_write.py` импортирует. Дублировать нельзя: это ровно тот код,
  который уже стоил отладки на живом сервере.

Новая доменная ошибка `PermissionDeniedError` в `errors.py`.

## Общие решения

### Часовые пояса

`start`/`end` принимаются как ISO-строки:

- naive (`"2026-08-20T15:00"`) → читается как локальное время
  `config.timezone`. Это основной случай: пользователь говорит «в 15:00», и
  LLM не должен угадывать offset — ошибка тут даёт встречу, сдвинутую на
  часы, при внешне успешном вызове;
- со смещением (`+03:00`, `Z`) → уважается как есть.

Парсинг через `datetime.fromisoformat`, при неудаче — `InvalidArgumentError`
с примером формата (по образцу существующего `_parse_date`). Далее —
`EWSTimeZone.from_zoneinfo(config.timezone)`, не голый `ZoneInfo`
(см. CLAUDE.md про `find_free_slots`).

### Приглашения участникам

Дефолт — **отправлять**. Дефолт «не отправлять» создаёт тихий разрыв между
тем, что человек считает сделанным, и тем, что произошло: встреча есть,
участник не знает, обнаруживается в момент начала. Ошибочное приглашение
видно сразу и лечится извинением; неотправленное не видно до провала.

Булев параметр схлопывает три значения EWS в два:

- `send_invitations=True` (дефолт) → `SendToAllAndSaveCopy`;
- `send_invitations=False` → `SendToNone`;
- нет участников → `SendToNone` независимо от флага (слать некому).

`SendOnlyToAll` наружу не выставляется: копия в «Отправленных» — то, что
человек ожидает по опыту Outlook. Аналогично `send_cancellations` в
`delete_event`.

Риск неверного адресата закрывается не выключением отправки, а требованием
к участникам: **только email-адреса, никогда имена**. Строка без `@`
отклоняется. В docstring прямо: если известно только имя — сперва
`resolve_person`, и при нескольких кандидатах переспросить пользователя, а
не выбирать самому. `resolve_person` по построению возвращает список
кандидатов по частичному имени, поэтому защита ставится там, где
неоднозначность реально возникает.

Каждый ответ содержит явное `invitations_sent` / `cancellations_sent`,
чтобы LLM мог точно сказать пользователю, что произошло.

### Повторяющиеся встречи

В этой версии — правка экземпляра, без работы с сериями:

- `Single` → обычная правка;
- `Occurrence` / `Exception` → правка одного экземпляра (порождает
  исключение в серии) — штатный путь;
- `RecurringMaster` → `InvalidArgumentError`: «это правило серии; правка
  серии целиком не поддерживается, передайте event_id конкретной встречи из
  list_events».

`item_type` уже вычисляется в `format_event_summary`, отдельная логика
определения типа не нужна.

**Швы под будущую полную поддержку** (заложены сразу, иначе переход сломает
контракт tools):

1. `scope: str = "occurrence"` присутствует в сигнатуре `update_event` и
   `delete_event` с самого начала. Единственное допустимое значение —
   `"occurrence"`; `"series"` даёт `InvalidArgumentError` «не
   поддерживается». Переход к полной поддержке — снятие проверки, не
   изменение контракта.
2. `create_event` принимает `recurrence: dict | None = None` одним
   объектом, а не россыпью плоских полей (`recurrence_type`,
   `recurrence_interval`, …). Сейчас допустим только `None`, иначе
   `InvalidArgumentError`.

При соблюдении швов доработка до полной поддержки аддитивна: маппер
паттернов exchangelib (`DailyPattern`, `WeeklyPattern`, `*MonthlyPattern`,
границы `end`/`number`), снятие двух запретов, тесты. Переписывать
написанное не придётся. Отдельно потребуется живая проверка правки серии с
уже накопленными исключениями — Exchange ведёт себя там неочевидно.

### Занятость не проверяется

`create_event` и `update_event` не проверяют, свободен ли слот, и не зовут
`find_free_slots` внутри. «Найди время и поставь встречу» — два вызова,
которые LLM делает сам. Внутренняя проверка сделала бы tool
непредсказуемым (создал/не создал по неявному критерию) и удвоила бы число
EWS-запросов на каждую запись.

### Тело встречи

`body` принимается как plain text. Чтение уже делает HTML→text
(`html_to_text`), запись симметрична. HTML не принимается: сценария, где
LLM нужно верстать разметку, нет, а инъекция разметки в чужой календарь —
лишний риск.

## `create_event`

```python
create_event(
    subject: str,
    start: str,
    end: str,
    attendees: list[str] | None = None,
    optional_attendees: list[str] | None = None,
    location: str | None = None,
    body: str | None = None,
    all_day: bool = False,
    send_invitations: bool = True,
    recurrence: dict | None = None,
) -> dict
```

**All-day.** При `all_day=True` из `start`/`end` берутся только даты, время
игнорируется. `end` — **включительный** день: пользователь говорит «отпуск
с 20 по 22», а не «по 23». Это единственное место, где входная дата не
равна уходящей в EWS, — поведение проверяется на живом сервере и
фиксируется в CLAUDE.md.

All-day — это булев флаг `is_all_day` на item, а не встреча `00:00–23:59`:
такая встреча без флага закрасит день как занятый и отобразится полосой, а
не плашкой, и в free/busy пойдёт как `Busy`, а не `Free`. Подделать
временем нельзя.

**Валидация до любого обращения к EWS:** `end > start` (для all-day
`end >= start`), непустой `subject`, адреса через `_validate_emails`,
`recurrence is not None` → отказ.

**Ответ:** `format_event_details(item, tz)` — та же структура, что у
`get_event`, включая `event_id` для последующей правки — плюс
`"invitations_sent": bool`. Совпадение формы важно: LLM уже знает эту
структуру.

## `update_event`

```python
update_event(
    event_id: str,
    subject: str | None = None,
    start: str | None = None,
    end: str | None = None,
    location: str | None = None,
    body: str | None = None,
    attendees: list[str] | None = None,
    send_invitations: bool = True,
    scope: str = "occurrence",
) -> dict
```

Порядок: получить item по `event_id` (общий `_fetch_one` с
ChangeKey-fallback) → проверить право на правку → применить переданные поля
→ `item.save(send_meeting_invitations=...)`.

**`None` = «не менять».** Очистка полей не поддерживается — явно сказано в
docstring. Пустая строка в `subject` — ошибка, а не очистка. Различение
`null`/`""` намеренно не вводится: модели путают эти значения, а цена
ошибки — тихая порча чужого календаря. Плоские типизированные параметры
выбраны вместо словаря `changes`, чтобы схема tool оставалась
самодокументирующейся — LLM видит точный список изменяемых полей. При
необходимости очистка добавится отдельным `clear_fields: list[str]` без
изменения сигнатуры.

**Изменение времени** (несимметрично — по намерению, стоящему за фразой):

- передан только `start` → длительность **сохраняется**, `end` едет следом.
  Это перенос: «перенеси на 16:00» не должно менять длительность;
- передан только `end` → `start` на месте, длительность **меняется**. Это
  «продли до 17:00» / «давай закончим в 16:30»;
- переданы оба → берутся как есть.

Docstring формулируется в терминах намерения: «чтобы перенести встречу,
передавайте `start` (длительность сохранится); чтобы изменить длительность,
передавайте `end`; чтобы задать новые границы — оба».

Ошибка до обращения к EWS, если результирующий `end <= start` (в том числе
когда передан только `end`, оказавшийся раньше существующего `start`).

**`event_id` в ответе перечитывается с item после `save()`.** При
обновлении экземпляра серии EWS возвращает новый id (см. комментарий про
`OccurrenceItemId` в `Item.save` в exchangelib) — переиспользовать входной
`event_id` нельзя, клиент получил бы id, по которому потом не найдёт
встречу.

**Право на правку.** Менять может только организатор. Определяется до
записи сравнением `item.organizer.email_address` с `config.ews_email`
(регистронезависимо); если организатор не определяется — полагаемся на
отказ EWS. Ошибки EWS транслируются в `PermissionDeniedError` с текстом
«встречу может изменить только организатор», а не отдаются сырым кодом.
Актуальный список для exchangelib 5.6.0 (проверен на установленной
библиотеке): `ErrorCalendarIsNotOrganizer`, `ErrorAccessDenied`,
`ErrorCalendarCannotUpdateDeletedItem`, `ErrorCannotDeleteObject`. Класса
`ErrorCannotUpdateObject` в этой версии **не существует**.

## `delete_event`

```python
delete_event(
    event_id: str,
    send_cancellations: bool = True,
    scope: str = "occurrence",
) -> dict
```

Та же проверка организатора и та же логика по типам item, что в
`update_event`.

**Если пользователь не организатор — удаление не выполняется.** Удаление
чужой встречи из своего календаря — по смыслу отклонение приглашения
(уведомляющее организатора), это другая операция, и подменять одну другой
нельзя. Явный отказ с объяснением, что нужен отдельный инструмент.

**Ответ:** `{"deleted": true, "event_id": ..., "subject": ...,
"cancellations_sent": bool}`. `subject` возвращается, чтобы LLM мог
подтвердить пользователю, *что именно* удалено.

## Обработка ошибок

Без отклонений от существующего правила: каждый tool ловит
`OutlookMcpError` и возвращает `exc.to_dict()` как обычный результат.
Исключения не пробрасываются через MCP-протокол. Новая
`PermissionDeniedError` наследует `OutlookMcpError` и сериализуется так же.

## Тестирование

**Юнит-тесты — новый файл `tests/test_calendar_write.py`**
(`test_calendar_service.py` уже 1013 строк).

Фейки `CalendarItem` расширяются в `tests/conftest.py`. Действует главный
урок проекта: **фейк обязан повторять реальный контракт exchangelib**, а не
то, как API «логично выглядит» — баг с `WorkingPeriod.weekdays` не поймали
~60 зелёных тестов именно из-за фейка, хранившего удобное представление.
По каждому записываемому полю (`is_all_day`, `required_attendees` /
`optional_attendees` как `Attendee`/`Mailbox`, `organizer`, `start`/`end` с
`EWSTimeZone`) типы сверяются с исходниками exchangelib. Фейковые
`save()`/`delete()` записывают переданные kwargs — тесты проверяют не
только результат, но и какое значение `send_meeting_invitations` реально
ушло.

Покрытие:

- `create_event`: naive-время читается в `config.timezone`; время с offset
  уважается; `end <= start` → ошибка до EWS; all-day (включительный `end`,
  флаг `is_all_day`); `send_invitations` True/False → правильная
  EWS-константа; без участников → `SendToNone` независимо от флага;
  `recurrence` не `None` → ошибка;
- `update_event`: только `start` → длительность сохранена; только `end` →
  начало на месте; только `end` раньше `start` → ошибка; `None`-поля не
  затрагиваются; `RecurringMaster` → отказ; `Occurrence` → правка проходит;
  не организатор → `PermissionDeniedError`; `scope="series"` → отказ;
- `delete_event`: `send_cancellations` → правильная константа; не
  организатор → отказ; `RecurringMaster` → отказ;
- `EWS_ALLOW_WRITE=0` → пишущие tools отсутствуют в `tools/list`
  (в `test_server.py`);
- ошибки EWS транслируются в доменные; tools возвращают `to_dict()`, а не
  бросают.

**Ручная проверка на живом Exchange обязательна.** История проекта прямая:
`WorkingPeriod.weekdays`, путь `sender`, наивное время от
`GetUserAvailability`, `list_events` с сериями — всё прошло юнит-тесты и
сломалось только вживую. Для записи цена ошибки выше: страдает чужой
календарь.

Порядок — от безопасного к рискованному, все шаги на встречах **без
участников**, кроме шага 5:

1. `create_event` без участников → проверить в Outlook время, дату, тему;
2. `update_event` переносом и растягиванием → проверить;
3. all-day на 2 дня → плашка, а не полоса; второй день включён;
4. `delete_event` → встреча исчезла;
5. `create_event` **с одним участником** (свой другой адрес или
   согласившийся коллега) → приглашение дошло; затем `update_event`
   (обновление дошло) и `delete_event` (отмена дошла);
6. `update_event` на экземпляре серии → изменился один экземпляр, серия
   цела;
7. `update_event` на чужой встрече → внятный отказ, а не EWS-код.

По итогам живой проверки CLAUDE.md пополняется разделом про запись — всё
найденное вживую фиксируется там, как для остальных подсистем.

## Документация

- README: раздел «Не делать» переформулируется («никакой записи в почту;
  календарь — только через явные tools»);
- CLAUDE.md: перестаёт называть сервер read-only, получает описание модуля

## Вне области

- Создание повторяющихся встреч и правка серий целиком (швы заложены);
- отклонение/принятие чужих приглашений;
- очистка полей в `update_event`;
- запись в почту в любом виде;
- проверка занятости внутри пишущих tools.
