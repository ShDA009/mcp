# postgres-mcp

MCP-сервер для PostgreSQL: health-чеки, анализ медленных запросов, explain-планы, подбор индексов. **Сторонний код**, не наш — используем готовый пакет [crystaldba/postgres-mcp](https://github.com/crystaldba/postgres-mcp) (MIT, PyPI `postgres-mcp`). Здесь — только конфигурация подключения и установочные скрипты, исходников сервера в этом репозитории нет.

Транспорт — stdio, потребитель — Cline. Запускается через `uvx` (рекомендуется) или в Docker (`crystaldba/postgres-mcp`).

## Установка для сотрудников (uvx, без Docker)

Готовые установочные скрипты в [install/](install/) — под Windows, macOS (Apple Silicon) и Linux. Скрипт проверяет/ставит `uv`, спрашивает строку подключения к БД и режим доступа, сохраняет `.env` и генерирует **лаунчер** (`~/.config/postgres-mcp/launch.sh` на macOS/Linux, `launch.ps1`/`launch.cmd` на Windows), который прописывается в Cline вместо прямого вызова `uvx`. Инструкция — [install/README.md](install/README.md).

### Почему лаунчер, а не `uvx` напрямую в конфиге Cline

Версия пакета (`POSTGRES_SPEC` — минорная ветка, см. ниже) не зашивается в `cline_mcp_settings.json`. Лаунчер при каждом старте сервера подтягивает файл [`mcp-versions.txt`](../mcp-versions.txt) из корня репозитория и берёт версию оттуда — если поднять диапазон там и запушить, обновление доезжает до всех сотрудников без переустановки, максимум за несколько минут (кеш GitHub CDN). Если сеть недоступна — используется локальный кеш последнего успешного запроса, а если кеша тоже нет (самый первый запуск без сети) — вшитый в лаунчер fallback.

Из сети лаунчер получает **только строку со спецификатором версии**; она не исполняется как код, а после проверки регуляркой на допустимые символы подставляется в команду запуска.

### Версии

Диапазон зафиксирован в [`../mcp-versions.txt`](../mcp-versions.txt) (`POSTGRES_SPEC`) — минорная ветка (например `postgres-mcp>=0.3,<0.4`): патчи и security-фиксы внутри неё подтягиваются автоматически, переход на следующую минорную/мажорную ветку требует правки этого файла и коммита. Еженедельный workflow [`.github/workflows/check-upstream.yml`](../.github/workflows/check-upstream.yml) заводит issue, если у upstream вышла версия за пределами текущего диапазона.

### Два пина в лаунчере, помимо версии пакета

Оба нужны из-за незакрытых верхних границ у upstream — проверено запуском, без них сервер не стартует:

- **`--python 3.13`** — зависимость `pglast==7.2.0` публикует колёса только до `cp313`. На машине с Python 3.14 `uvx` иначе уходит в сборку из исходников (нужны `make` и компилятор) и падает.
- **`--with "mcp[cli]<2"`** — upstream объявил `mcp[cli]>=1.5.0` без верхней границы, а в `mcp` 2.0 удалён модуль `mcp.server.fastmcp`, на импорте которого сервер падает с `ModuleNotFoundError`.

Когда upstream починит границы у себя, оба пина можно снять — это константы в начале `install/setup.sh` и `install/setup.ps1`.

## Режим доступа

У сервера два режима, задаются флагом `--access-mode` (переменной окружения для него нет — лаунчер подставляет флаг сам, читая `PGMCP_ACCESS_MODE` из `.env`):

| Режим | Что можно | Когда |
|---|---|---|
| `restricted` | только чтение, read-only транзакции | по умолчанию, для прод-БД |
| `unrestricted` | чтение, запись, DDL | дев-базы |

Установщик спрашивает режим и по умолчанию ставит `restricted`.

## LLM-фича: статус в нашем контуре — **выключена**

У upstream есть экспериментальная **альтернативная** стратегия подбора индексов через LLM. Основной (детерминированный) подбор индексов от неё не зависит и работает всегда.

**В нашем контуре она не работает, и это осознанное решение — фичу пропускаем при установке.** Причина: имя модели захардкожено в upstream как `gpt-4o` ([`llm_opt.py:156`](https://github.com/crystaldba/postgres-mcp/blob/main/src/postgres_mcp/index/llm_opt.py#L156)), переменной окружения для него нет, а наш корпоративный шлюз это имя не обслуживает и на такой запрос отвечает:

```
No matching route found. It is likely because the model specified in your request
is not configured in the Gateway.
```

Что теряется: только альтернативная стратегия подбора индексов. Health-чеки, анализ медленных запросов, explain-планы и основной подбор индексов работают в полном объёме.

### Если понадобится включить

Технически перенаправление работает: сервер создаёт клиент как `OpenAI()` без аргументов, поэтому официальный `openai`-SDK сам берёт адрес и ключ из окружения —

```bash
OPENAI_BASE_URL=<адрес корпоративного шлюза>/v1
OPENAI_API_KEY=<корп-ключ>   # шлюз требует настоящий, на плейсхолдер отвечает 401
```

— но упрётся в имя модели. Варианты, по возрастанию цены:

1. **Смапить `gpt-4o` на обслуживаемую шлюзом модель** — единственный вариант без своего кода. Требует запроса к владельцам шлюза.
2. **Прокси-шим** — локальный сервис переписывает поле `model` и проксирует на шлюз; в `.env` тогда адрес шима. Плюс один процесс на машине каждого сотрудника.
3. **Форк upstream ради одной строки** — противоречит правилу «не форкать» ниже и тянется через все обновления.

Отдельно учтите: `instructor` требует от модели structured output по JSON-схеме, так что даже после подмены имени фича может падать на валидации ответа — то есть ни один из вариантов не гарантирует результата.

Ещё нюанс на будущее: `OPENAI_BASE_URL` в upstream-README не документирован — он работает как штатная переменная `openai`-SDK, а не как фича самого postgres-mcp. При мажорном обновлении пакета это стоит перепроверить (например, если клиент начнут создавать с явными аргументами).

## Сборка и запуск (Docker, альтернатива)

```bash
docker run -i --rm --env-file .env crystaldba/postgres-mcp --access-mode=restricted
```

Через `-e` (если не хочется `--env-file`) — но тогда строка подключения к БД видна в списке процессов:

```bash
docker run -i --rm \
  -e DATABASE_URI="postgresql://user:pass@host:5432/db" \
  -e OPENAI_BASE_URL="http://host.docker.internal:1234/v1" \
  -e OPENAI_API_KEY="local" \
  crystaldba/postgres-mcp --access-mode=restricted
```

## Конфигурация (`.env`)

Скопировать [.env.example](.env.example) и заполнить реальными значениями:

```bash
DATABASE_URI=postgresql://user:password@db.example.com:5432/dbname

# Читает лаунчер (сервер получает режим флагом --access-mode):
PGMCP_ACCESS_MODE=restricted

# Опционально — только для LLM-варианта подбора индексов:
OPENAI_BASE_URL=http://host.docker.internal:1234/v1
OPENAI_API_KEY=local

PYTHONUNBUFFERED=1
```

`.env` не должен попадать в репозиторий (заигнорирован в `.gitignore`). Установочные скрипты пишут его за вас в `~/.config/postgres-mcp/.env`.

## Не делать

- Не патчить и не форкать upstream без явной необходимости — пин минорной ветки в `mcp-versions.txt` уже даёт защиту от несовместимых изменений.
- Не передавать `DATABASE_URI` через `-e`/`env`-секцию в конфиге Cline — только через `.env`, который сервер (или лаунчер, при uvx-запуске) читает сам: в строке подключения лежит пароль от БД.
- Не ставить `unrestricted` на прод-БД — сервер выполняет SQL, который сформировала модель.
